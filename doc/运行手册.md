# 运行手册

这份手册用于将"古河商城公司客服 Agent"项目在本机运行起来。推荐方式是：

- Docker 启动 MySQL 和电商主应用 `ecommerce-service`
- Agent 后端使用 `agent-steps/` 里的逐步快照在本机启动，便于按项目观察 Prompt、LangChain / LangGraph、RAG、Tool、HITL、Trace 和 Eval 的演进
- 用户商城和管理后台前端已构建并集成到 `ecommerce-service`，由 Spring Boot 静态托管
- 古河商城客服 Agent 调试后台仍可在本机单独启动，用于 trace、reasoning 和 eval 演示
- Chroma 容器是可选项；逐步 Agent 后端默认优先使用本地配置和本步代码目录内的 Chroma 持久化数据

当前 `docker-compose.infra.yml` 的实际服务是 `mysql`、`ecommerce-service` 和可选的 `chroma`。Agent 后端不包含在 Docker Compose 配置中；商城和管理后台前端不需要再单独启动开发服务器。

下文命令默认从项目代码仓库根目录执行。项目代码仓库根目录即包含 `agent-steps/`、`ecommerce-backend/`、`frontend/` 和 `docker-compose.infra.yml` 的目录。不同电脑上的项目存放位置不同，请先在终端进入你克隆下来的代码仓库根目录，再执行手册里的相对路径命令。

根目录的 `.env` 用于 Docker Compose，内含 MySQL 数据库名、本地演示密码和服务令牌；第一次运行前从 `.env.example` 复制一份为 `.env`（默认值即可本地联调）。需要自己填写的只有 `agent-steps/guhe.env` 里的模型 API Key。

## 1. 环境要求

- Docker Desktop
- Java 17+
- Python 3.13+
- Node.js 20.19+ 或 22.12+（调试后台使用 Vite 8）
- npm

安装 Docker Desktop 后，请先启动 Docker Desktop，等待 Docker Engine 启动成功。

Windows PowerShell：

```powershell
docker --version
docker compose version
```

macOS Terminal：

```bash
docker --version
docker compose version
```

国内网络下第一次拉取 MySQL、Maven、JDK/JRE 镜像可能较慢。可以在 Docker Desktop 的 `Settings -> Docker Engine` 中添加下面的镜像源配置，保存后点击 `Apply & Restart`：

```json
{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://docker.1ms.run",
    "https://hub.rat.dev"
  ]
}
```

注意：如果 Docker Engine JSON 中已有其他字段，不要整段覆盖，只将 `registry-mirrors` 合并进去。

## 2. 配置模型 API Key

Agent 后端通过 OpenAI 兼容接口调用模型。默认示例使用硅基流动，你也可以换成其他 OpenAI 兼容平台。

如果使用硅基流动，先登录 `https://cloud.siliconflow.cn/`，进入 API 密钥页面（`https://cloud.siliconflow.cn/account/ak`），点击"新建API密钥"生成自己的 Key。这个 Key 只填写到你本机的 `guhe.env` 文件里，不需要提交给项目，也不要通过聊天工具发送、截图分享或提交到代码仓库。

### 2.1 创建统一配置文件

项目逐步代码快照共用一份模型配置。第一次准备环境时，复制 `guhe.env.example`：

Windows PowerShell：

```powershell
copy agent-steps\guhe.env.example agent-steps\guhe.env
notepad agent-steps\guhe.env
```

macOS Terminal：

```bash
cp agent-steps/guhe.env.example agent-steps/guhe.env
open -e agent-steps/guhe.env
```

这里的 `agent-steps/guhe.env` 是相对于项目代码仓库根目录的文件，不是固定的电脑绝对路径。

### 2.2 最小可用配置

打开 `agent-steps/guhe.env` 后，至少确认以下配置存在。模板已按硅基流动预填了聊天模型、分类模型、Embedding 模型和 reranker 模型，通常只需要把 `AGENT_OPENAI_API_KEY` 换成你自己的 Key：

```env
AGENT_OPENAI_API_KEY=你的模型平台 Key
AGENT_OPENAI_BASE_URL=https://api.siliconflow.cn/v1
AGENT_OPENAI_MODEL=Qwen/Qwen3-8B
AGENT_CLASSIFIER_MODEL=Qwen/Qwen3-8B
AGENT_EMBEDDING_MODEL=BAAI/bge-m3
AGENT_RAG_RERANK_ENABLED=true
AGENT_RAG_RERANK_MODEL=BAAI/bge-reranker-v2-m3
AGENT_RAG_RERANK_BASE_URL=https://api.siliconflow.cn/v1
AGENT_LOG_LEVEL=INFO
AGENT_ACCESS_LOG=false
```

> 如果你的 `guhe.env.example` 中包含 `AGENT_RAG_RERANK_INSTRUCTION`，可按模板保留。该字段为英文 reranker 指令，直接传给模型，用于引导重排序策略。

配置说明：

- `AGENT_OPENAI_API_KEY` 不要上传或分享，也不要通过截图或聊天记录泄露
- 聊天、分类、Embedding、reranker 默认共用硅基流动的 OpenAI-compatible 地址和同一个 Key
- 如果硅基流动提示模型不存在、没有权限或当前账号不可用，到模型广场选择可用的聊天模型、Embedding 模型或 reranker 模型，再替换对应的 `AGENT_OPENAI_MODEL`、`AGENT_CLASSIFIER_MODEL`、`AGENT_EMBEDDING_MODEL` 或 `AGENT_RAG_RERANK_MODEL`
- 逐步后端会按自己的项目阶段决定是否使用 RAG、Tool、Workflow、HITL、Trace 或 Eval
- 如果更换了 Embedding 模型，建议删除对应 step backend 下的 `.chroma` 后重启 Agent，让知识库重新向量化
- `AGENT_LOG_LEVEL` 控制项目终端日志详细程度；`AGENT_ACCESS_LOG=false` 默认隐藏 Uvicorn 的逐请求访问日志

### 2.3 项目代码快照的统一配置

这些模型参数已按硅基流动预填好。运行项目代码时，你通常只需要改 `AGENT_OPENAI_API_KEY`。项目 step 后端默认调用真实 OpenAI-compatible 模型接口。

这份 `guhe.env` 是本机私有文件，不要上传或分享。后续每一步的 Agent 后端都会优先读取它，所以项目里不再为每一步单独配置 `STEP03_OPENAI_API_KEY` 这类临时变量。

### 2.4 选择日志详细程度

Step 02–41 共用标准 Python 日志级别，不增加项目专属级别。配置值从精简到丰富依次为：

- `ERROR`：最少，只显示本轮能力执行失败
- `WARNING`：显示异常、降级、兜底和错误
- `INFO`：默认的学习级别；每轮显示请求开始、Agent 路径摘要和本步关键观察，具体数量随当前链路变化，最多 7 条
- `DEBUG`：需要深入对照代码时使用；除了 `INFO` 内容，还会显示项目 Prompt、脱敏后的用户输入与历史、文本模型输入输出、RAG 查询与片段、Tool 参数与业务返回结构（Payload）、Observation、Workflow 状态、reranker 候选分数和 Evaluation 逐 Case 结果

启动时会先打印一次当前步骤；后续日志不再重复步骤。常规日志格式统一为“时间｜级别｜事件码｜session_id｜中文摘要”。下面省略 RAG 事件末尾的字段字典，方便先观察主链路：

```text
10:23:40.001｜INFO   ｜GUHE_LOGGING_READY｜-｜项目日志已启动，步骤=step-41-final-rehearsal，level=INFO，access_log=False
10:23:45.120｜INFO   ｜CHAT_REQUEST_STARTED｜demo-001｜收到聊天请求，输入长度=20
10:23:45.122｜INFO   ｜RAG_RETRIEVAL_PLAN｜demo-001｜rag.hybrid_retrieval.build_retrieval_plan｜RAG 检索计划已生成：先改写查询，再限定知识域
10:23:45.126｜INFO   ｜RAG_RETRIEVAL_CACHE_MISS｜demo-001｜rag.hybrid_retrieval.retrieve_knowledge｜检索缓存未命中，开始执行双路召回
10:23:45.132｜INFO   ｜RAG_DUAL_RECALL｜demo-001｜rag.hybrid_retrieval.retrieve_knowledge｜向量召回与关键词召回已分别完成
10:23:45.136｜INFO   ｜RAG_FUSION_RANKED｜demo-001｜rag.hybrid_retrieval.retrieve_knowledge｜双路候选已融合并按最终得分排序
10:23:47.411｜INFO   ｜CHAT_PATH_SUMMARY｜demo-001｜意图=promotion_query → RAG=2 → Tool=none → Workflow=none → Model=used，耗时=2291.0ms
```

日志会在对应步骤实际发生时输出，不会等回答完成后再反向拼接整条链路。因此，你可以根据相邻日志的时间观察路由、检索、工具、工作流和模型各自发生在什么时候，也能看出哪个步骤耗时较长。不同项目和不同问题会经过不同路径，没有执行的环节不会打印。

把日志级别改为 `DEBUG` 后，你可以在启动后端的终端里对照项目代码查看更多细节。`REQUEST_DETAIL` 在请求进入时输出；每次实际模型调用会在调用前后输出 `MODEL_INPUT` 和 `MODEL_OUTPUT`；RAG、Tool、Observation、Workflow、Hook、Safety、Trace、Cost 和 Evaluation Case 也会在各自模块完成当前步骤时输出对应事件。最后的 `CHAT_PATH_SUMMARY` 只汇总本轮已经发生的路径，不重新打印前面的详情。

这些详情会保留项目 Prompt、RAG 文本和 Tool 业务结构，但会自动遮蔽能够识别的 API Key、Token、Authorization、Cookie、密码、身份标识、昵称、手机号、地址和邮箱等凭据或个人隐私。隐藏推理不会写入日志；你看到的是结构化判断依据或公开的 reasoning summary。Embedding 只显示模型、输入数量和维度，不打印完整向量数组。

请使用项目演示数据，不要输入真实用户的隐私信息。第三方 HTTP 和模型 SDK 日志默认保持在 `WARNING`。前端 Trace 只展示适合公开查看的执行摘要，和终端里的 `DEBUG` 演示日志用途不同。

`AGENT_ACCESS_LOG=false` 时隐藏 Uvicorn access log；需要观察 HTTP 访问时可以改为 `true`。配置非法时日志级别回退到 `INFO`。修改 `guhe.env` 后需要停止并重新启动当前 step 后端才会生效。

### 2.5 在项目代码中增加自己的日志

如果你在练习中增加了新的路由、检索步骤、工具或工作流节点，建议继续使用项目共享日志，不要直接使用 `print()`。这样新增日志会自动沿用当前级别、事件格式、`session_id` 和脱敏规则。

普通调试事件可以使用 `log_guhe_event()`。下面假设当前代码中已经有 `rewritten_query` 和 `allowed_topics` 两个变量；实际使用时，请换成你所在步骤的真实变量：

```python
from guhe_runtime.guhe_logging import log_guhe_event

log_guhe_event(
    "RAG_PLAN_READY",
    "检索计划已生成",
    observe=True,
    rewritten_query=rewritten_query,
    allowed_topics=allowed_topics,
)
```

- 事件码使用稳定的英文大写下划线形式，例如 `RAG_PLAN_READY`、`TOOL_RESULT_CHECKED`
- 第二个参数用简短中文说明刚刚完成了什么，不要把整段响应拼进摘要
- `observe=True` 表示这是默认 `INFO` 下值得观察的关键调试事件；省略该参数时只在 `DEBUG` 下显示
- 业务细节通过命名字段传入，便于共享工具统一格式化和脱敏，不建议先拼成一整段字符串
- 日志应紧跟在事件实际发生的位置：计划生成后记录计划，检索完成后记录命中；Tool 没有使用共享装饰器或 Hook 时，再在开始和结束位置分别记录，不要重复打印已有的 Tool 生命周期日志
- 不要等最终回答生成后再补打一串过程日志，否则时间顺序和耗时观察都会失真

`INFO` 每轮只把前 7 条关键调试事件保持为 `INFO`，第 8 条及以后的调试事件会改按 `DEBUG` 级别处理：使用 `INFO` 配置时不显示，切换到 `DEBUG` 后可以看到。如果新增调试事件在 `INFO` 下没有出现，先检查是否设置了 `observe=True`、是否已经超过本轮前 7 条，再切换为 `DEBUG` 确认代码是否执行。不要为了显示更多内容而把所有事件都提升到 `INFO`。

遇到已处理的异常或降级，可以使用同一个项目 logger 记录标准 `WARNING`；本轮能力执行失败时使用 `ERROR`：

```python
import logging

from guhe_runtime.guhe_logging import LOGGER_NAME

logger = logging.getLogger(LOGGER_NAME)
logger.warning(
    "检索结果低于置信度阈值，已切换为安全兜底",
    extra={"event_code": "RAG_LOW_CONFIDENCE"},
)
```

`ERROR` 的写法相同，把 `logger.warning(...)` 换成 `logger.error(...)`，并使用能够说明失败位置的事件码。`@observe_chat` 和 `@observe_operation(...)` 会在一次请求或操作开始时建立日志上下文；在它们管理的链路内调用时，日志会自动带上当前 `session_id`，在启动阶段或请求链路外调用时则显示为 `-`。

`log_model_input()`、`log_model_output()`、`log_embedding_summary()` 和 `@observe_tool_execution` 同样从 `guhe_runtime.guhe_logging` 导入。模型输入输出和 Embedding 摘要在 `DEBUG` 下显示；Tool 装饰器会生成 `INFO` 生命周期事件和 `DEBUG` 输入输出详情。已有 Hook 或共享装饰器的 Tool 不要再次手工记录相同事件。

共享日志会遮蔽能够识别的敏感字段，但这不表示可以主动写入敏感数据。不要记录 API Key、Token、Authorization、Cookie、密码、真实手机号、真实地址、隐藏推理或完整 Embedding 数组。修改代码后重启当前 step 后端，再发起一轮请求，就能在启动终端中查看新增事件。

## 3. 启动项目

建议开两个终端窗口：一个运行 Docker 电商主应用，一个运行某一步 Agent 后端。只有需要使用古河商城客服 Agent 调试后台时，才额外打开第三个终端启动 `frontend/`。

### 3.1 启动 Docker 电商后端

Windows PowerShell：

```powershell
docker compose -f docker-compose.infra.yml up -d --build
```

macOS Terminal：

```bash
docker compose -f docker-compose.infra.yml up -d --build
```

第一次执行会拉取 Docker 镜像，并在容器里用 Maven 构建电商后端，耗时可能较长。构建日志停在 `RUN mvn ... dependency:go-offline` 或 `RUN mvn ... package` 一段时间不动，通常是在下载 Maven 依赖，并不一定是卡住。如果因为网络中断或 Maven 依赖下载失败而退出，重新执行同一条命令即可。

`ecommerce-backend/docker/m2-cache.tar.gz` 是可选的 Maven 预热依赖缓存（约 145 MB），因超过 GitHub 单文件上限而不随仓库提交。如果本机有这份文件，Docker 构建会先把它解压到构建容器的 Maven 本地仓库，再补充下载缺失依赖；没有这份文件时 Dockerfile 会自动改为全部从远程下载，首次构建会更慢但结果一致。后续在同一台机器上重新构建时，Docker BuildKit 会复用 Maven 缓存，通常会比第一次快很多。

检查容器状态：

```bash
docker compose -f docker-compose.infra.yml ps
```

检查电商后端健康状态：

```powershell

```

macOS Terminal：

```bash

```

返回 `{"status":"UP"}` 表示电商后端可用。接口文档地址：

阶段五、六的新前端访问地址：

## 4. 运行项目逐步代码快照

这一章只服务于"古河商城售后协同 Agent"项目代码快照。项目代码仓库里的 Agent 后端以逐步快照为准，用来观察每一步如何从最小聊天入口逐步构建出 RAG、Tool、Workflow、HITL、Trace、Eval 和成本治理能力。

项目快照主要涉及这些目录：

```text
agent-steps/guhe.env
requirements.txt
docker-compose.infra.yml
ecommerce-backend/
agent-steps/step-xx-*/backend
frontend/
```

### 4.1 复用同一套 Python 和模型配置

### 4.6 项目常见问题

#### 没有 API Key 能不能运行

不能完整运行需要真实模型回答的 step 后端。你可以先准备环境、启动服务框架、检查健康接口和观察基础响应；但正式运行时必须填写 `AGENT_OPENAI_API_KEY`。

#### 填了 Key 但模型调用失败

检查三件事：

- `AGENT_OPENAI_API_KEY` 是否完整。
- `AGENT_OPENAI_BASE_URL` 是否仍然是 `https://api.siliconflow.cn/v1`。
- 模型平台账号是否有可用额度。

#### 调试后台很多区域是灰色

这是正常的。每一步只开放当前讲过的能力。Step 03 没有 RAG、Tool、Trace、Eval、HITL，相关区域就应该置灰。

#### 端口被占用

如果 `8000` 被占用，可以换端口启动当前 step 后端，并同步修改调试后台目标地址。

```bash
PORT=8001 python main.py
```

如果某一步代码还没有读取 `PORT`，就先停止占用 `8000` 的旧进程，再启动当前 step。

## 8. 常见问题

### 8.1 `curl localhost` 返回代理错误

如果看到 `Privoxy`、`proxy` 或类似代理错误，使用跳过代理的命令：

Windows PowerShell：

```powershell
curl.exe --noproxy '*' http://localhost:8000/health
```

macOS Terminal：

```bash
curl --noproxy '*' http://localhost:8000/health
```

### 8.2 端口被占用

本项目默认端口：

- MySQL：`3306`
- 电商后端：`8081`
- Agent 后端：`8000`
- Chroma 容器：`8001`
- 新商城和管理后台：随电商后端使用 `8081`
- 古河商城客服 Agent 调试后台：`5173`

如果端口已被占用，先确认是不是当前项目已经启动，不要重复启动同一个服务。

### 8.3 模型认证失败

如果 Agent 返回 `401`、`Unauthorized` 或认证失败：

- 检查 `agent-steps/guhe.env` 中的 `AGENT_OPENAI_API_KEY` 是否完整
- 检查模型平台账号、余额或免费额度是否可用
- 检查 `AGENT_OPENAI_BASE_URL` 是否是 OpenAI 兼容接口地址
- 如果模型名称不可用，到模型平台复制一个可用的小模型名称替换后重启 Agent

### 8.4 Agent 无法访问电商后端

本机运行 Agent 时，`AGENT_ECOMMERCE_BASE_URL` 应该是：

```env
AGENT_ECOMMERCE_BASE_URL=http://127.0.0.1:8081
```

不要写成 `http://ecommerce-service:8081`。`ecommerce-service` 这个服务名只适合 Docker 容器内部互相访问；当前仓库没有 Agent 容器。

### 8.5 Docker Compose 没有启动 Agent 和前端

这是当前仓库的预期行为。`docker-compose.infra.yml` 的实际服务可以用下面命令核对：

```bash
docker compose -f docker-compose.infra.yml config --services
```

当前会看到：

- `mysql`
- `ecommerce-service`，对外暴露 `8081:8081`
- `chroma`，可选，对外暴露 `8001:8000`

Agent 后端需要按本手册在本机单独启动。用户商城和管理后台已内置在 `ecommerce-service`，不需要单独启动 `ecommerce-backend/frontend` 的开发服务器。

### 8.6 容器访问不到独立 Agent

默认配置是：

```env
AGENT_SERVICE_BASE_URL=http://host.docker.internal:8000
```

排查顺序：

1. 在宿主机执行 `curl --noproxy '*' http://localhost:8000/health`，确认 Agent 本身可用。
2. 确认 Agent 启动日志监听的是 `0.0.0.0:8000` 或宿主机可访问地址。
3. 如果 Docker 环境不支持 `host.docker.internal`，用宿主机局域网 IP 覆盖 `AGENT_SERVICE_BASE_URL` 后重启 `ecommerce-service`。

### 8.7 前端页面能打开但 API 返回 401 或 403

`401` 表示还没有登录或登录态已失效；重新登录对应角色即可。`403` 表示角色不匹配，例如普通用户访问 `/api/admin/**`，或管理员访问 `/api/shop/**`。

### 8.8 `doc.html` 被 SPA 页面覆盖

当前安全和路由配置已放行 `/doc.html`、`/v3/api-docs/**`、`/swagger-ui/**` 和 `/webjars/**`。如果打开 `http://localhost:8081/doc.html` 看到商城页面，先重新构建镜像：

```bash
docker compose -f docker-compose.infra.yml up -d --build ecommerce-service
```

再检查 `ecommerce-service` 日志中 Knife4j / springdoc 是否正常启动。

### 8.9 MySQL 初始化数据缺失或重复

初始化数据由 `ecommerce-backend/src/main/java/com/guhe/mall/config/DataInitializer.java` 写入。重复启动时会先检查已有数据，避免重复插入预设账号、商品、余额和订单。

如果需要重置演示数据，可以清理 Docker volume 后重启：

```bash
docker compose -f docker-compose.infra.yml down -v
docker compose -f docker-compose.infra.yml up -d --build
```

这会删除本地 MySQL 和 Chroma 容器数据，只适合演示环境重置。
